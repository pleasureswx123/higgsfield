1 适用范围与技术选型

本规范约束 higgsfield-frontend/ 的全部新业务代码，作为实现和代码评审依据。管理平台继续使用 ruoyi-fastapi-frontend/vue3/web/ 的 Vue3 工程；父目录中的其他框架版本不是本项目管理端构建目标。管理端新增及修改的业务代码同样遵守根目录 AGENTS.md 的 Vue3、分层和双主题约束；本规范不要求重写未涉及的已有管理端代码。

平台 技术基线 组件库
制作平台 Vue3、TypeScript、Vite、Vue Router、Pinia、统一 Axios 客户端 Element Plus 与 shadcn-vue 共存，按业务需求选择最合适的组件；保留 Tailwind 样式方案
管理平台 本地已有 Vue3、JavaScript、Vite、Vue Router、Pinia、Axios 沿用现有 Element Plus 管理界面，不因制作端共存方案而要求引入另一套组件库

两个前端独立构建，共用若依后端。API 以平台 API 契约为准；数据模型以数据库详细设计为准；整体边界见技术架构方案。供应商 API Key 仅在后端治理，不进入制作端代码、Store 或浏览器存储。

1.1 制作端新增代码规则

前端技术栈统一为 Vue3 + Vue Router + Pinia + Axios。higgsfield-frontend 新增业务组件统一使用 <script setup>，禁止 Options API；制作端保留 TypeScript，因此采用 <script setup lang="ts">。管理端沿用已有 JavaScript 工程，不因此强制转换全部存量代码。业务逻辑抽离为 use 开头的 composables，接口请求独立放 api/，全局状态使用 Pinia，不引入 Vuex。此前“优先”或“禁止默认使用”的宽松措辞不再适用。

路由管理必须使用 Vue Router：路由表、模块和导航守卫集中在 router/；应用内导航使用 RouterLink 或 router.push/replace，页面通过 useRoute/useRouter 获取路由上下文。路由守卫负责登录和页面访问控制，但不能代替后端资源鉴权。Axios 是普通 HTTP 请求的统一客户端；文件上传、下载也由 api/ 封装。P0-4 已定义的 Bearer SSE 使用专用 fetch 流适配模块，这是传输协议适配，不能据此在组件内直接写请求。

2 六项强制编码规范

编号 强制要求 实施与评审标准
FE-01 全部使用 Vue3 <script setup>，使用组合式 API，禁止 Options API 制作端业务单文件组件使用 <script setup lang="ts">；不以 data/methods/mounted 等 Options API 编写新业务组件，不并列维护两套组件范式
FE-02 业务逻辑抽离为 use 开头的 composables 如 useAssetLibrary、useUploadSession、useGenerationEvents；负责复用的状态、流程及生命周期清理。纯格式化/转换工具放 utils，不为了命名把纯函数包装成 composable
FE-03 API 请求统一抽离单独模块，不在组件内直接写请求 URL、请求参数、响应类型、传输实现集中在 api/；组件不直接调用 axios、fetch、XMLHttpRequest 或拼接口路径。SSE/分片上传也经过专用传输模块，不作为例外散落在组件中
FE-04 组件拆分遵循单一职责 页面负责布局与用例装配；业务组件负责明确业务交互；基础组件负责展示。使用显式 props/emits 传递数据和事件，避免一个组件同时管理请求、全局状态、复杂弹窗与全部列表逻辑
FE-05 状态管理使用 Pinia，不使用 Vuex 跨组件/页面共享状态放 Pinia；单组件临时状态使用 ref/reactive，不为所有变量建立 Store。两套前端各自维护 Store 实例，不共享运行时状态
FE-06 命名、导出及 ref/reactive/computed 写法贴合 Vue3 组合式开发习惯 采用 §5 的明确规则；组件、composable、Store、API 模块保持一致命名与类型约束，避免响应式丢失及隐式副作用

这些规则适用于本项目编写的业务组件与逻辑。第三方依赖内部实现不因本规范被修改；引入或生成的组件仍需检查公共接口与样式集成，不能把第三方示例中的请求代码直接复制进业务组件。

3 模块职责与依赖方向

以下为目标目录，不表示这些工程文件已经创建：

higgsfield-frontend/

  src/
    router/                   Vue Router 路由定义、模块和导航守卫
    api/
      client.ts               统一认证、错误处理及请求基础设施
      projects.ts             项目接口及 DTO
      assets.ts               素材接口及 DTO
      generations.ts          生成任务接口及 DTO
      uploads.ts              分片与完成协议
      task-events.ts          Bearer fetch 流与任务事件解码
    composables/              use 开头的业务组合式函数
    stores/                   Pinia 跨页面共享状态
    views/                    路由页面与用例装配
    components/
      ui/                     shadcn-vue 基础组件
      shared/                 确有复用需求的展示组件与适配封装
      assets/                 素材业务组件
      creation/               创作业务组件
    types/                    公共类型；API 模块也可就近声明专属 DTO
    utils/                    无 Vue 生命周期依赖的纯函数
    styles/                   设计变量、主题及样式集成

页面/业务组件通过 composables 或 Store action 执行业务流程；composables 和 Store 使用 api/ 中的函数。业务操作统一由 composable 或 Store action 调用已封装的 API 函数；组件保留展示、事件转发和必要的局部 UI 状态，不承载接口编排。API 模块不导入页面、组件或业务 Store；统一客户端通过受控认证适配读取凭据，避免 api 与 stores 循环依赖。

Store 管理共享状态及状态动作，composable 管理可复用的交互流程；同一份事实不在两处复制维护。服务器分页结果、草稿、任务快照分别确定唯一状态来源，派生状态用 computed，不能靠互相 watch 维持双份数据一致。

4 Element Plus 与 shadcn-vue 共存规则

不规定所有页面必须来自同一库，也不规定同一种业务永远只能选择某个库。选择依据是功能匹配、参考界面还原、键盘操作、数据量、维护成本及项目实际集成效果，形成简短选型记录。

场景 选择原则
复杂表单、表格、日期选择、树形数据 优先评估 Element Plus 是否满足交互及性能需求；若采用 Element Plus 表单，使用 ElForm 校验及显式提交处理
创作工作区、媒体卡片、定制菜单及轻量交互 评估 shadcn-vue 的组合与定制方式，结合既有设计变量实现统一视觉
素材目录树 大量节点场景评估 el-tree-v2；定制文件树评估 shadcn-vue File Tree。按实际节点规模、展开/选择、搜索及菜单需求验证后决定，不根据截图直接认定性能结论
弹窗、抽屉与表单组合 一个交互容器由一套组件管理焦点、Esc、打开关闭及校验；不要在同一弹窗叠加两套焦点锁或两个表单校验系统

共存必须完成以下集成检查：

  • 统一颜色、字号、间距、圆角、亮色/暗黑双主题和交互状态，建立项目变量到 Element Plus 与 shadcn-vue 主题变量的映射。
  • 明确 CSS 导入顺序与 Tailwind reset/preflight 处理，验证按钮、输入框、表格等默认样式；禁止用大范围全局选择器覆盖另一组件库内部样式。
  • 统一弹层层级和挂载策略，验证 Teleport 后的主题继承、滚动锁、键盘导航及焦点返回。
  • 根据实际使用组织组件和样式导入，检查构建体积，不默认同时全量注册两个组件库。
  • 基础组件名字保持可辨识，例如 ElButton 与项目 Button；只在确有统一业务语义时封装适配组件，避免为每个库组件机械包一层。

上述检查是工程初始化后的验收要求，尚未实测；不在本次文档更新中安装依赖或初始化组件库。

5 命名、导出与响应式约定

对象 规范
组件 文件与组件名称使用 PascalCase，例如 AssetCard.vue；props/emits 明确定义类型，子组件不修改 props 或其内部对象
Composable 文件与函数使用 useXxx，例如 useAssetLibrary.ts / useAssetLibrary；使用具名导出，返回有含义的 refs、computed 和动作函数
Store 文件按领域命名，如 project.ts；导出 useProjectStore，Store ID 唯一且稳定；禁止引入 Vuex
API 函数 具名导出，动词表达操作，如 listAssets、createGeneration；统一参数对象和响应类型，禁止多个组件重复定义同一 DTO
变量与动作 camelCase，布尔值使用 is/has/can 等语义前缀；事件处理器使用 handleXxx；类型/接口使用 PascalCase；不把任意变量都写成全大写常量
ref 用于标量、可替换对象、DOM/组件引用；在脚本中正确使用 .value，模板按 Vue 的模板解包规则使用，不以类型断言掩盖错误
reactive 用于需要整体组织且身份稳定的对象；不直接替换响应式代理；需要解构状态时使用 toRefs，避免普通解构丢失响应式
computed 用于派生值，getter 不发请求、不写其他状态；只有需要明确双向映射时使用可写 computed，setter 必须有清晰语义
watch 仅用于副作用或外部同步；明确依赖和触发时机，避免无边界 deep watch；异步请求处理取消或过期响应，防止旧结果覆盖新选择
Pinia 解构 状态/getter 使用 storeToRefs；动作可直接调用或解构，不通过普通对象复制创建第二份共享状态
生命周期 定时器、订阅、事件监听、上传及 SSE 连接必须有明确清理；页面离开停止本地订阅不等于取消服务器生成任务

优先使用 const；只对需要重新赋值的局部变量使用 let。API ID 保留十进制字符串，金额和大整数遵守 P0-4，禁止转 Number 后再提交。未知数据在 API 边界校验，不在业务组件内用 any 或任意断言绕过类型检查。

6 项目业务边界

上传、任务事件及生成请求分别封装；SSE 接收与解码属于 api/，订阅生命周期和页面状态协调属于 useGenerationEvents 等 composable。必须遵循 P0-4 的 revision、Idempotency-Key、事件游标和权限错误处理；不能因组件库选择而改写业务协议。

统一 HTTP 客户端处理公共传输错误；字段错误由表单展示，业务冲突保留用户输入并提示刷新。禁止在组件、composable 和客户端对同一错误重复弹出提示。前端 allowedActions 只控制展示，后端权限仍是最终判断。

组件库选择不改变目录和部署：管理端、制作端手动启动；PostgreSQL 和 Redis 使用 Docker；共用后端手动启动。制作端工程尚未初始化，此规范与 AGENTS.md 不代表功能已实现。

7 代码评审与后续验证

每次制作端变更核对 FE-01～06、API 模块边界、组件职责、共享状态来源和两套组件样式共存。工程初始化时落实 TypeScript 检查、Vue 规则及格式检查；自动化门禁须实际配置后才能宣称生效。

验证按改动风险选择：纯展示改动检查目标页面；上传续传、生成幂等、任务事件重连、权限失效和复杂状态流程使用有意义的契约或交互测试。不要为只镜像实现的简单逻辑机械增加测试。检查结果区分静态检查、组件交互、后端联调与真实模型调用，不将前端通过构建等同于业务端到端完成。

8 分层执行基线

前端统一 Vue3 + Vue Router + Pinia + Axios，业务组件全部采用 <script setup>，禁止 Options API。页面（views）负责路由级装配；组件（components）负责单一展示与交互；use 组合函数（composables）负责业务流程和生命周期；api 模块负责接口及传输封装。业务组件调用组合函数或 Store action，不直接发请求。Vue Router 管理路由与导航，Pinia 管理全局状态，Axios 承担普通 HTTP 请求。命名、具名导出和响应式用法遵循本规范 §5，不以组件库示例绕过分层。

9 Vue3.4+ 双向绑定规范

本节适用于 higgsfield-frontend 的自定义业务组件。制作端 Vue 版本基线至少为 3.4，工程初始化时锁定兼容的 Vue、编译器及组件库版本；本次未安装或升级依赖。管理端继续沿用已有 Vue3 工程，不据此重写存量代码。

自定义组件双向绑定优先使用 defineModel()；命名模型使用 defineModel('xxx')，对应父组件的 v-model:xxx。多个模型分别声明、分别更新，不使用 .sync。该用法依据 Vue 官方组件 v-model 文档。

以下仅为文档中的绑定示意，不是已创建的业务组件：

<script setup lang="ts">
const title = defineModel<string>('title', { required: true })
const open = defineModel<boolean>('open', { required: true })
</script>

<template>
  <input v-model="title" />
  <button type="button" @click="open = false">关闭</button>
</template>

父组件通过 v-model:title="title" 和 v-model:open="isOpen" 分别绑定已初始化的状态；无参数模型使用 defineModel<T>() 对应默认 v-model。

项目评审要求：

  • 子组件严禁直接修改 props，包括对象或数组的嵌套值。使用模型 ref 的赋值或显式事件请求父层更新；对象模型更新应创建新对象再赋给 model.value，避免通过共享引用绕过更新事件。
  • defineModel 已声明对应模型属性和更新事件，不重复用 defineProps/defineEmits 声明同名模型协议。普通单向输入和业务事件仍分别使用 defineProps/defineEmits。
  • 父组件负责初始化受控模型值。子组件不以默认值掩盖父层未初始化状态；必要时使用 required 约束，检查父子初始值一致。
  • 禁止用双向 watch 复制一份模型状态来模拟 v-model。需要取消编辑的表单可明确维护本地草稿，确认时再提交，不能自动回写取消的编辑。
  • 对 Element Plus 或 shadcn-vue 的封装，遵循底层组件实际暴露的模型名称及事件，以适配层映射；不修改第三方内部 props，也不强制改写第三方源码。

以上与既定页面、组件、use 组合函数、api 模块分层同时执行；双向绑定仅负责组件状态交互，不在模型 setter 中隐藏网络请求或费用消费。

10 若依后端协议适配

统一 Axios 客户端解析框架 code/msg/success/time；普通业务失败可能 HTTP 200，必须按业务 code 处理。分页读取顶层 rows/pageNum/pageSize/total/hasNext，不使用 data.items/nextCursor。业务错误细分读取 data.errorCode，兼容框架仅有 msg 的异常；SSE 建连先检查 Content-Type，JSON 认证错误不能当事件流。异步受理用 data.status/statusUrl 区分。普通前端分层和 defineModel 规范保持不变，详见后端编码与框架对齐规范。

11 UI 截图还原与亮暗双主题

本节为用户确认的 UI 强制要求，后续页面实现和视觉验收必须遵循。参考材料为用户提供的截图与 已整理截图状态对照表。实现前核对具体页面及状态；静态截图用于视觉依据，不单独证明点击、悬停或加载行为。

11.1 两种主题保持同一界面设计

页面视觉、布局结构及组件排版以对应截图为准，保留导航位置、内容分区、卡片比例、表格密度、表单对齐、侧边栏缩进、按钮形状和操作层级。不能用 Element Plus 或 shadcn-vue 的默认外观代替参考效果。

必须同时交付亮色版和暗黑版，并提供主题切换功能。截图所属主题保留原有配色特征；另一主题保持同一品牌识别、状态语义和视觉层次，调整具体色值以适配背景。保留配色特征不意味着将深色背景上的文本颜色原封不动搬到亮色背景。两种主题使用同一布局和组件结构，不维护两套逐渐分叉的页面。

11.3 主题切换行为

  • 工作区固定提供可发现且可键盘操作的亮色/暗黑切换入口；图标配合可访问名称，明确当前模式或切换目标。
  • 主题由一个 Pinia Store 管理，通过 useTheme 组合函数提供切换行为，集中同步根节点主题标记；两个组件库不能维护彼此独立的主题开关。
  • 显式选择保存在本地非敏感偏好中；初始化优先恢复已保存选择，没有选择时读取系统偏好作为初始值。用户显式选择后不被系统变化覆盖。“跟随系统”可作为后续额外选项，不替代必需的亮/暗切换。
  • 首次绘制前尽早应用主题，避免先亮后暗闪烁；偏好不可读写时仍可切换，不能阻塞页面。
  • 切换不刷新页面、不重置路由、筛选、展开项、表单草稿、上传进度和任务订阅；退出页面时按既有规范清理监听。
  • 图片、视频、用户上传素材和模型结果保持原始颜色，禁止整体 invert/filter；只有承载界面及预览控制层切换主题。

11.4 双主题验收

同一页面、同一尺寸和同一数据分别检查两种主题：卡片、表格、表单、侧边栏、按钮及弹层的布局一致；截图已有主题进行直接对照，另一主题核对视觉语义和层级。覆盖默认、悬停、聚焦、选中、禁用、错误、加载和空状态，检查文字/边框可辨识、键盘焦点、弹层主题继承、刷新后偏好恢复和切换时业务状态保留。

验收记录需同时提供亮色、暗黑页面证据，不能仅检查首页或单个组件。本次仅明确规范；主题切换、两套最终色值及视觉实现尚未编写，不将文档检查等同于界面验收。
