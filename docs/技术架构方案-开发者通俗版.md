# 制作平台技术架构：从一次生成请求理解整个系统

版本：1.0  
日期：2026年10月27日  
读者：参与开发、希望先理解整体流程的程序员  
定位：解释版。字段、接口和事务约束以详细设计为准；下文不是已实现代码说明。

## 1. 先看系统里究竟有什么

这套系统的主体是两个前端、一个后端业务工程，以及从后端业务工程运行起来的后台任务进程。

```text
制作前端 Vue3                管理前端 RuoYi Vue3
项目、元素、生成、查看        用户、权限、模型、价格、预算
          └─────────┬──────────┘
                    ↓
              FastAPI业务后端
          登录鉴权、业务校验、任务受理
                    │
       ┌────────────┼─────────────┐
       ↓            ↓             ↓
   PostgreSQL     Redis        后台Worker进程
   业务事实       缓存与队列       │
                         ┌───────┴────────┐
                         ↓                ↓
                      供应商API          公司NAS
                      生成图片视频       保存媒体
```

**Worker是后台执行程序，不是另一个模型。** 它调用供应商API、查询任务，或把结果下载到NAS。API请求不需要一直挂着等待几十秒甚至几分钟的生成。

这里不是要先拆成很多微服务。API和Worker可以共享同一个后端工程的业务代码，分别启动进程。分开运行是为了隔离短请求和长任务，并能分别控制并发。

本地Docker只启动PostgreSQL和Redis；后端、两个前端及需要运行的Worker在宿主机启动。正式环境部署方式由运维确认。架构图里的“容器”表示一个应用或进程边界，不等于Docker容器。

## 2. 哪些东西放哪里

| 位置 | 保存什么 | 不应混淆的内容 |
|---|---|---|
| PostgreSQL | 项目、元素、任务、文件索引、权限、用量、费用、待办事件 | 数据库保存媒体元数据与关联，长期媒体文件放NAS |
| NAS | 上传的图片、生成图片、视频及预览文件 | 文件存在不代表所有人都有访问权 |
| Redis | 缓存、任务队列通知等 | 队列消息不能成为唯一任务记录 |
| 浏览器 | 当前输入、选择、筛选和展示状态 | 不能决定真实权限、费用或长期任务状态 |
| 供应商 | 执行模型推理，可能提供临时结果链接 | 临时URL不能替代NAS归档 |

浏览器通过平台授权接口预览和下载。后端根据文件索引读取NAS，不把NAS共享路径直接暴露给用户。供应商读取参考图时也不能直接使用公司内网路径，需要适配器按验证过的上传或注册方式准备素材。

## 3. 先区分图片文件、素材、元素和作品

假设我们准备一个“女孩”角色：

```text
元素：女孩
  └─ 当前修订R3
       ├─ 正面图素材的固定版本（主图）→ NAS文件A
       ├─ 侧面图素材的固定版本       → NAS文件B
       └─ 背面图素材的固定版本       → NAS文件C
```

- **文件（StoredFile）：** NAS上的具体字节，以及大小、格式、哈希和状态。
- **素材（Asset）：** 可被组织和复用的媒体业务对象，例如“女孩正面图”。
- **素材版本（AssetVersion）：** 指向确定文件的不可变版本。换图创建新版本，不覆盖旧文件。
- **元素（Element）：** 角色、场景或道具，可以包含多张素材图片。
- **元素修订（ElementRevision）：** 固定某一次元素的图片列表、主图和参与生成的描述。
- **作品（Output）：** 某次生成任务产出的图片或视频。转为素材后，可以复用同一个NAS文件，不必再复制字节。

为什么要分这么细？因为修改角色主图之后，昨天生成的视频仍应能查到昨天使用的图片。若所有任务都指向“当前角色图片”，历史输入会随编辑漂移。

一个元素可以先没有图片。有图片时必须恰好有一张主图；无图元素不能直接充当有效的图片参考。审核状态Approved也不能替代这项检查。

“我的元素”是有权限元素的聚合视图，创建和生成仍需明确项目。公司公共素材库当前暂缓，不要把聚合视图做成全公司公开库。

## 4. 用户点击生成后，代码实际做什么

以已经选好角色图片、提交视频生成为例：

### 第一步：前端整理输入

创作区收集项目、媒体目录、提示词、模型版本、参数，以及具体图片版本。前端可以做即时校验，例如提示“这个模型不支持所选时长”，但后端必须重新校验。

`@女孩`不只是一个字符串。编辑器保存referenceKey，引用清单保存元素修订、素材版本和媒体角色。编译器依据同一清单生成提示词里的图片编号和供应商媒体数组，避免文字指“图片1”、实际却传错图。

### 第二步：API受理任务

请求进入GenerationService，它检查：

1. 用户是不是当前项目成员，是否有生成权限。
2. 图片是否已就绪、是否具有使用权。
3. 模型是否已发布，参数和参考图数量是否合法。
4. 是否已受理过同一次提交。
5. 预算是否允许本次预计消费。

检查通过后，在**一次数据库事务**中完成预算预占、任务及输入快照保存、Outbox事件保存，然后返回任务编号。这里返回成功表示“平台已接单”，不是“视频生成成功”。

### 第三步：后台执行

Outbox投递程序把任务通知送到Redis队列。生成Worker领取后，按阶段准备参考素材、编译供应商请求、取得任务固定的凭据版本并调用供应商。

供应商可能同步返回图片，也可能返回视频任务ID。同步图片直接进入结果处理；异步任务按原任务ID查询。两种情况不能强行使用同一种响应解析和轮询流程。

### 第四步：归档与更新页面

后台先记录结果，再由媒体Worker下载或解码、校验并保存到NAS。文件就绪后，作品标记为归档成功。前端通过SSE收到状态更新，也可以重新查询任务恢复显示。

费用处理独立推进：图片已保存但用量还没确认时，可以显示“结果可用，费用待确认”。不能把结果成功、归档成功和结算成功合成一个布尔值。

## 5. Outbox为什么需要一张数据库表

假设代码先保存任务，再给Redis发消息。在这两步之间崩溃，就会出现“任务在数据库里，但没有Worker知道要处理它”。

Outbox把“需要通知Worker”也存进数据库，与任务一起提交：

```text
同一个PostgreSQL事务
  保存任务 + 预占预算 + 保存Outbox待办
  要么全部成功，要么全部撤销

事务之外
  投递程序读取待办 → 发到Redis → 标记已投递
```

因此即使Redis暂时不可用，待办还在数据库中。服务恢复后可以继续投递。这就是“Outbox的本地事务”：本地指同一个数据库事务，不是开发电脑。

但是消息发出后、标记前崩溃，可能再次投递。所以Worker要识别重复消息。Outbox解决漏通知风险，**不能单独保证供应商只被调用一次**。

## 6. 幂等、租约、事务各解决什么问题

| 机制 | 典型问题 | 我们的处理 |
|---|---|---|
| 幂等键 | 双击生成、网络重传 | 同键同请求返回原任务；同键不同内容报冲突 |
| revision/CAS | 两个人同时编辑同一元素 | 保存时比较修订号；旧版本提交不能覆盖新修改 |
| Worker租约 | 两个进程同时拿到同一任务 | 只有有效领取者推进阶段；过期执行者不能覆盖新状态 |
| 数据库事务 | 写了一半就失败 | 相关数据库更新一起提交或撤销 |
| Outbox | 数据已写入，通知丢失 | 数据库保留待投递事件，后续补投 |

**最需要谨慎的是供应商提交超时。** 超时可能表示对方已接单，只是响应没有回来。此时记录submission_unknown并核查，不能像普通查询一样自动重发付费POST。

供应商网络调用放在数据库长事务之外。不要为了等待生成，一直占着数据库连接和行锁；也不要让多个并发任务共享同一个AsyncSession。

## 7. 供应商适配器做什么

平台内部希望用统一方式表达“提交生成”“查询结果”，但供应商接口字段和返回结构可能不同。ProviderAdapter定义这些操作，具体适配器负责翻译。

| 平台概念 | 供应商适配负责的事情 |
|---|---|
| 模型版本 | 解析为准确调用名，例如mm-gemini-3.0-p |
| 底层模型名称 | 按确认映射记录为NBPro / NBP，与调用名分开 |
| 参考素材 | 上传、取得临时URL或注册Asset，按账号与区域限制使用 |
| 提示词与图片列表 | 编译为该接口接受的字段、角色和顺序 |
| 返回结果 | 解析图片载荷、任务ID、状态、结果来源与用量 |

同一个显示名称不应让前端随意拼接供应商调用名。前端提交modelVersionId，后端根据配置确定准确别名和能力版本。菜单只显示已授权发布的模型；价格表有某个规格，不代表接口一定支持。

NB、image2、Seedance和H3各自验证。文本聊天、语音及图中预留的stream_chat目前不属于首期实现要求。

## 8. UsageNormalizer和计费模块怎样分工

UsageNormalizer读取响应或后续查询中的usage，转换成统一用量，例如输入Token、输出Token、视频时长。它保留来源、区分未知值，并避免把轮询多次返回的同一份累计用量重复计入。

UsageBilling再用任务固定的价格版本计算费用：

```text
供应商响应
  → 用量解析与标准化
  → 匹配正确计费项与单位
  → 按任务价格版本计算
  → 更新预算及费用记录
  → 后续与供应商账单核对
```

例如Token计价是“数量÷计价基数×单价”，H3秒数计价则不能套Token公式。金额使用Decimal和数据库numeric，避免浮点误差。

预占是接单时暂时占住额度，不是提前认定实际消费。缺usage保持待确认，不填零；NAS保存失败也不表示供应商没有收费。

## 9. 生成的图片怎样加入角色，再用于视频

这条流程有两个独立生成任务，图片任务和视频任务分别记录用量与费用。

```text
打开角色 → 进入图片创作 → 图片任务 → NAS归档
                                      ↓
                               用户挑选满意图片
                                      ↓
                          转素材 → 保存角色的新修订
                                      ↓
                          @选择角色 → 视频任务 → NAS
```

转素材和保存角色不是一个跨文件系统的大事务。转素材已经成功、角色保存发生revision冲突时，图片和素材仍保留；用户重新加载角色后再保存，不需要重新付费生图。

注意两个状态：作品的archiveState是**archived**，关联文件的state是**ready**。两者满足且权限允许后，才能进入后续素材引用流程。

元素目录用于整理角色、场景、道具；媒体目录用于保存图片和视频结果。二者不能混用。提交后用户切换页面不改变结果落点；原媒体目录被删除时，结果回到项目媒体根，并记录回退原因。

## 10. 前端怎样组织，后端怎样落代码

前端用Vue3、TypeScript、Vue Router、Pinia和Axios。页面负责组织布局，业务组件负责创作框、元素库等交互，composables封装业务行为，api模块统一请求。Stores管理需要跨组件共享的状态，不把所有局部表单都放进全局。

参数面板从后端能力配置获取可选项，不能给所有模型都展示同一套时长、数量和分辨率。SSE用于推送任务状态，不是传视频流；断线后重新鉴权并恢复状态。关闭浏览器不自动取消后台任务。

后端沿用仓库现有分层：

```text
controller：接请求、验证输入格式、使用统一响应
    ↓
service：判断业务规则、组织事务、调用适配器
    ↓
dao：执行数据库查询和写入
    ↓
entity/do：数据库模型；entity/vo：输入输出模型
```

Worker复用Service执行业务，不另建一套权限和计费规则。架构图中Worker到数据库的箭头表示数据依赖，不表示可以绕过分层直接随意写SQL。外部网络调用由业务编排在数据库长事务外执行。

数据库是PostgreSQL，主键使用bigint自增；API中的业务ID用十进制字符串，避免JavaScript精度问题。无物理外键意味着Service事务和校验必须承担关联完整性，不意味着可以省略关联检查。

## 11. 遇到失败时，先判断失败发生在哪一段

| 失败位置 | 应采取的动作 |
|---|---|
| 平台受理事务失败 | 回滚任务、预算与Outbox；前端保留输入 |
| 通知Worker失败 | 根据Outbox再次投递 |
| 上游提交结果未知 | 保留核查状态，不盲目重新生成 |
| 查询上游失败 | 使用原任务ID退避查询，不新建生成 |
| NAS归档失败 | 重试原结果保存；来源过期则按能力刷新或人工处理 |
| 元素回填冲突 | 保留作品和素材，重新读取元素修订再保存 |
| 用户权限撤回 | 新消费前阻断；已提交上游的任务继续后台归档和计费，用户访问重新鉴权 |

数据库事务不能回滚已经发生的外部生成，也不能与NAS写文件组成同一个原子事务。因此需要明确阶段、幂等记录和失败补偿。“补偿”是把不完整状态修复到可解释的结果，并不是把所有事情都撤销成没发生。

## 12. 开发时建议按这个顺序阅读和实现

1. 对照页面基线，明确项目、文件夹、元素和创作区的用户操作。
2. 落实权限、数据模型、上传归档和固定版本引用。
3. 实现任务受理、预算与Outbox，再接图片适配器，完成图片闭环。
4. 完成选图加入元素、@引用编译和视频适配，验证异常恢复。
5. 补齐首期协作、用量对账、双主题及真实项目验收。

前期可以用模拟供应商结果检查流程，但不能将其当作真实模型能力、费用和NAS环境验收。公司公共素材、Canvas、Chat、AI Director暂缓；详细文档保留未来结构，不意味着当前必须全部编码。
