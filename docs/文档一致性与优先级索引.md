## 2 编号、优先级与状态分开管理

| 维度 | 统一格式 | 含义与禁止混用 |
|---|---|---|
| 文档编号 | P0-1～P0-6 | 六份前置设计文档的稳定编号；尾数表示文档身份，不表示需求等级 |
| 需求优先级 | P0（阻断项）、P1（首期必需）、P2（后续增强） | 只使用这三种名称；表格和文字均用完整写法，不以“最高/高/中/低”另建映射 |
| 技术实施阶段 | ST-00～ST-06 | 依赖顺序，见架构 §12.1；不使用 P0～P6 代指阶段 |
| 业务交付批次 | B1～B4 | 业务交付里程碑，B2 演示不代表首期完成 |
| 需求身份 | PRJ/AST/ELM/GEN/COL/ADM/BIL/UX/QLT-两位编号 | 身份不随文档或实现批次变化；同 ID 继承 P0-1 规则表唯一等级 |
| 确认状态 | 基线、建议、门槛 | 基线是已确认不变量；建议待评审；门槛需证据验证；都不能代替优先级 |
| 实现状态 | 待实现、设计已补齐、验证通过等 | “设计已补齐”不等于接口、迁移、真实调用已通过 |
| 运行调度 | 路由 priority、队列调度、价格来源顺序 | 运行期数值/来源选择规则，不映射为上述需求等级 |

P0-1 的 69 条规则表是业务等级的唯一登记处，其他文档引用规则 ID，不能重新标级。一个规则包含首期能力和未来扩展时，表中等级只适用于首期部分；扩展使用独立 EXT 编号，不能整条降级。文档编号自身不赋予正文所有功能同一个等级。

## 3 等级定义与配套处理

| 优先级 | 判定标准 | 处理与退出规则 |
|---|---|---|
| P0（阻断项） | 权限、密钥、重复消费、预算一致性、不可变历史、数据完整性，或对应能力安全开放的前置契约 | 相关写路径/真实消费开放前实现并验证；未满足则关闭受影响路径，不以降级标签绕过。工程架构强制约束也必须满足 |
| P1（首期必需） | 首期已承诺的正常业务、组织交互、双主题与体验验收 | 可以按 B1～B4 排期，但首期交付前必须完成；不得当作“有空再做”。建议细节先评审，再实现 |
| P2（后续增强） | 已明确不纳入首期的扩展能力 | 不阻断首期；保留边界并关闭入口。进入首期须先做范围变更，更新源规则、API/数据库及验收 |

AGENTS.md 的 PostgreSQL、无物理外键、异步分层、框架响应、Vue3 写法及双主题均为强制约束，不因业务等级不同而豁免；双主题按 UX-08 登记为 P1（首期必需），在首期发布时同样必须通过。

D01～D10 是待决策项，不是可跳过的低等级需求。负责人和最迟时点沿用 P0-1；未确认时只阻断依赖该决策的实现/开放，不替用户批准建议。供应商 DIF-01～DIF-20 是差异记录，不是二十个新需求等级；其引用 GEN/ADM/BIL 规则，未验证的组合保持关闭。流式、Fast、4K 等条件能力不因表中有价格而被视为首期必开；三类模型基础链路仍须满足首期退出条件。

优先级变更必须记录规则 ID、原等级、新等级、原因、确认人、影响批次、接口/表及验收；先改 P0-1 唯一登记处，再同步引用和 HTML。若无范围变更确认，不将已承诺的 P1（首期必需）降为 P2（后续增强）。用例覆盖多条规则时，按其中最严格的开放门槛处理，不能另建互相冲突的用例等级。
