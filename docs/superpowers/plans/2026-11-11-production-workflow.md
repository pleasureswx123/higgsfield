# 制作协作闭环实施计划

**目标：** 项目成员能够完成分配、制作、提交具体版本、反馈返工、审核通过和固定版本引用，权限、页面和数据一致。

**依据：** 用户在本会话确认的完整业务闭环；旧 docs 仅作待核对线索。以下为实施计划，不代表已有能力或已验收结果。

**架构：** 沿用 controller → service → dao → entity，素材与元素共用流转规则，分别保存不可变审核版本。复用现有项目授权、事务锁、revision 和幂等机制。前端沿用 API、组合函数、组件分层。

**约束：** PostgreSQL、真实迁移、中文字段注释、双主题；不提交付费生成，不改供应商文档；测试数据与原有内容区分。使用 test-driven-development 验证关键规则，按 executing-plans 顺序实施。

## 1. 状态规则与版本证据

- [x] 新建 service/production_workflow.py 和 tests/test_higgsfield_production_workflow.py。以动作而非任意目标状态表达开始、提交、撤回、退回、通过；退回必填原因，提交与审核必须携带当前版本。
- [x] 扩展 entity/do/review_do.py、相关 VO、DAO 和真实迁移：审核事件保存目标、具体版本、执行人、动作、原因。旧历史不得臆造版本证据。
- [x] 素材 asset_lifecycle_service.py、元素 element_service.py 接入同一规则，旧状态入口也不得绕过规则；新版内容使当前状态回到制作中，旧通过证据保留。
- [x] 验证跳级审核、重复提交、过期版本、并发修改、幂等重放和回滚。

- [x] 验证查看者拒绝写入、跨项目访问拒绝、撤权及时生效、转交后旧制作人不能继续修改他人任务。
